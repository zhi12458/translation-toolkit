# Kimi K3 与 DeepSeek V4 Pro 语义模型实测记录（2026-08-13）

## 测试目的与边界

本次测试用于重新评估更新后的 `deepseek-v4-pro` 是否应替代 Kimi K3 承担中文源义
结构化分析。两条轨道均使用 `tests/fixtures/semantic-gold.json`、相同提示词和相同案例，
每个模型各运行三次，`reasoning_effort: high`，单次超时 300 秒。源义轨道不含英文，
中英审核轨道不含任何模型的 source-analysis。非法 JSON、Schema 失败和超时不修复后
计分。

测试时 DeepSeek 官方 API 的 `deepseek-v4-pro` 别名返回稳定 fingerprint
`a307abda487cd1b463329ccb945ce396`；官方模型页当日标示版本为
`DeepSeek-V4-Pro-0813`。报告只记录模型别名和 fingerprint，不据此猜测未公开的更新细节。

## 测试中发现并固化的 K3 请求问题

第一次 12 请求运行中，K3 六次均在约 0.3 秒收到 HTTP 400，而 V4 Pro 正常完成。
这不是模型超时或语义能力失败。进一步诊断发现，benchmark 的严格 JSON Schema 中有
若干只含 `enum`、未显式声明 `type: string` 的节点。通用 JSON Schema 允许这种写法，
但 Moonshot 当前严格 MFJS 接口拒绝该请求。

修复方式：

- 源义和审核响应 Schema 的全部字符串枚举同时声明 `type: string`。
- 不改变提示词、案例、字段或本地评分规则。
- 新增递归回归测试，确保所有 Kimi wire-schema 枚举均有显式字符串类型。
- live 失败不再统一记作 `failed`：本地输出契约失败记为 `schema_invalid`，安全保留
  HTTP 状态为 `http_NNN`，超时仍记为 `timeout`；任何供应商响应正文仍不落盘、不回显。

修复后 K3 源义三次全部通过严格 Schema，证明最初的零分报告无效，不得用于模型比较。

`得到谋生的食粮`案例中，两者三次都把获取者保留为 `null/ambiguous`。K3 三次都识别
`purpose + cost + progression`；V4 Pro 三次均识别 `purpose + progression`，但三次都漏掉
`cost`。K3 一次把“谋生的食粮”标为 `goal` 而非 `theme`；V4 Pro 一次把“丧生”的角色
标为 `theme`。K3 将该段标为 `needs_human`，V4 Pro 虽列出角色歧义却标为 `clear`。

两个模型都未达到源义轨道的歧义硬门槛，因此正式 selection 为 `null`。本次只有三个
源义案例，且 `condition-negation-source` 对 `判断.theme` 的金标值得再经人工校准；该结果
只能支持暂定分工，不能单独完成模型录用。

## 审核轨道与生产结论

V4 Pro 三次均返回本地 Schema 合法结果，无超时；blocking recall 为 `0.743590`，控制例
误报率为 `0`，三次字段一致率为 `0.2`，没有达到 blocker recall 1.0 的硬门槛。

K3 审核轨道未取得有效三次结果：一次长请求失败，另外两次供应商请求失败；单独诊断
也在 120 秒超时。因此不得把 K3 的审核零分解释为模型语义能力零分，但它在这一轨道的
当前生产可用性不足。

暂定结论保持：

- K3 继续作为中文源义结构化分析主候选，尤其重视目的、代价、递进等关系。
- V4 Pro 继续作为中英独立审核器，并作为疑难角色、指代和作用域的独立证据源。
- 不混拼两个模型的段落结果；谁可成为 canonical 仍由扩充后的同一金标集决定。
- 下一轮至少扩充省略主语、跨段指代、否定作用域、标题修饰关系和正确控制例后再各跑三次。
